# API package publication preparation

The user's September 4 overnight instruction forbids publication and deployment.
This workflow and its scripts are release preparation only. Do not push a release
tag or dispatch the workflow until the user authorizes publication again.

The workflow accepts only `api-packages-v<VERSION>` tags matching both exact RC
package versions and the client's exact contracts dependency. Manual dispatch
must select that matching tag, not a branch. Both packages are built and packed
before either is published. Lifecycle scripts are disabled during packing and
publication. The packed exports, file inventory and SHA-512 integrity are checked;
the manifest also records SHA-256, source ref and commit. The exact tarballs and
manifest are retained as a workflow artifact before publication starts.

Publication remains two npm operations, not an atomic transaction. Both registry
versions are checked before the first operation: only HTTP 404 permits a publish;
an existing version is skipped only when name, version and SHA-512 integrity match
the prepared bytes. Authentication, rate limiting and server failures stop the
workflow. A conflicting existing version stops the entire pair, including when
the other package is absent. Final verification requires both registry versions
to match the prepared artifacts.

## Recovery after partial publication

Keep the original release tag, source commit and workflow artifacts. Resolve the
transient failure, then rerun from that same tag with the same lockfile. The
workflow rebuilds and checks the regenerated bytes against any existing version;
it skips an identical published package and publishes only its absent partner.
If bytes differ, stop and inspect the original retained artifacts. Do not delete,
overwrite or blindly skip a conflicting npm version. Any necessary new RC pair
requires a new explicit version, consumer validation and release authorization.
Consumers must not cut over until both packages have verified registry provenance
and clean installs from the exact reviewed versions.

This does not configure npm trusted publishers, bootstrap unpublished packages,
establish repository provenance permissions, or prove consumer acceptance. Those
remain release prerequisites. No tokens are embedded in the scripts. Registry
checks use unauthenticated reads of the already-configured public npm registry.

Both manifests identify the exact case-sensitive `ClashKingInc/ClashKingAPI`
repository and their own monorepo directories. The local preflight rejects
missing/mismatched metadata or disabled provenance. A read-only GitHub check on
September 4 confirmed that repository is public; visibility must be rechecked
before a future release because npm provenance requires public source. This
metadata change does not change repository visibility or authorize publication.
See [npm provenance prerequisites](https://docs.npmjs.com/generating-provenance-statements/).
